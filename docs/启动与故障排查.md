# 运行指南

## Docker 启动

在项目根目录运行以下命令。Docker Compose 启动 MySQL 8.4、RocketMQ 5.3.2、两个 Redis 7.4.2 实例、MCP 资料服务、BGE 嵌入服务和 pgvector。两个 Redis 分别承载题目缓存和共享配额协调。后端通过 Flyway 迁移数据库，就绪后由 Nginx 提供网页。

```sh
docker compose --profile app up -d --build
```

打开 [职智达](http://localhost/)，在登录页进入演示空间，或注册账号保存自己的简历和练习记录。默认使用 Mock 模型，无需密钥。

自定义配置时，将根目录的 `.env.example` 复制为 `.env` 后修改；已有 `.env` 时直接编辑。首次启动前执行 `docker compose --profile app config --quiet` 检查配置。首次构建需要下载基础镜像、Maven 和前端依赖。

Compose 使用 `.env` 为配置文件中的变量赋值，容器接收各服务 `environment` 中列出的配置。标准文件已配置内部向量连接与检索参数；改用外部嵌入服务、向量库或提示词目录时，通过 Compose 覆盖文件显式传入，并为外部提示词挂载目录。分进程部署时，API 与 Worker 使用一致的模型、检索和提示词配置。

| 操作 | 命令 |
| --- | --- |
| 查看服务状态 | `docker compose --profile app ps` |
| 查看启动日志 | `docker compose --profile app logs -f backend frontend mysql` |
| 停止服务并保留数据卷 | `docker compose --profile app stop` |

## 从已有安装升级

先暂停任务提交，等待旧版面试、导入、索引和在途任务处理完成，再停止旧版实例。沿用已有 MySQL 和共享文件。若数据库已执行 V52，在目标应用库执行一次[题库种子升级 SQL](../scripts/sql/upgrade-v52-question-seed.sql)，再启动新版。该脚本仅将已发布 V52 的校验值 `1176925259` 更新为 `1976613928`。V53 下架四道旧种子题，保留既有练习和历史版本，以四个新 ID 加入 RocketMQ 题目。全新数据库直接启动即可。

两种派发模式配置为 `RUN_DISPATCH_MODE=rocketmq` 和 `KNOWLEDGE_DISPATCH_MODE=rocketmq`。源码进程连接 `127.0.0.1:8081`，Compose 内部连接 `mqproxy:8081`。可以通过 `docker compose logs mqinit` 核对资源初始化，通过 `docker compose exec mqbroker sh mqadmin consumerProgress -n mqnamesrv:9876 -g zhizhida-run-workers` 查询面试消费组的进度。自定义前缀时相应替换组名。核对受理、延迟投递、业务完成与资料导入后再开放写入。

使用外部集群时，将 `ROCKETMQ_ENDPOINTS` 指向 gRPC Proxy。`ROCKETMQ_RECEIVE_WAIT_MS` 须落在该 Proxy 允许的长轮询区间。仓库内的 Proxy 与 Worker 均配置为 200 毫秒。启用访问控制时，API 需要向 `run-ready`、`knowledge-import`、`knowledge-index` 发送通知。Worker 需要订阅这三个 Topic 以及 `run-delay`，使用 `run-workers`、`import-workers`、`index-workers` 消费组，并向 `run-delay` 和 `dispatch-invalid` 发送重试和诊断通知。上述名称均须加部署前缀。通过 `ROCKETMQ_ACCESS_KEY`、`ROCKETMQ_SECRET_KEY` 和 `ROCKETMQ_TLS_ENABLED` 配置连接。

回退时先停写，排空或登记仍在途的任务，停止新版实例。若回退到包含原 V52 的版本，在相同的应用库把上述脚本中的两个校验值对调执行，随后恢复旧版与对应配置。保留数据卷与知识文件，用数据库任务 ID 对账。在途面试使用受理时的模型配置和提示词指纹，接管任务的 Worker 须能加载相同版本。

## 本机启动

准备 JDK 21、Maven、Node.js 22.14 或更高，以及 Docker Compose。确保 `mvn --version` 显示 Java 21。Windows 可运行 `.\start.cmd --mock-ai`，其他平台使用同一启动器：

```sh
node scripts/dev.mjs --mock-ai
```

首次启动时，启动器通过 npm 调用 pnpm 9.15.9，按锁文件安装前端依赖。后续启动复用已安装的前端依赖，添加 `--install` 可重新安装。启动器等待 MySQL、Redis 和 RocketMQ 健康，编译后端，并启动本机 MCP 资料服务、后端和 Vite。终端显示「就绪」时打开[本机页面](http://127.0.0.1:5173/)。按 Ctrl+C 停止源码进程；停止依赖容器使用 `docker compose --profile middleware stop mysql redis redis-cache mqproxy mqbroker mqnamesrv`。

使用已有 MySQL 时，先创建项目数据库，给应用账号授予该库的建表和读写权限。在根目录 `.env` 中设置 `SPRING_DATASOURCE_URL`（例如 `jdbc:mysql://127.0.0.1:3306/zhizhida`）、`SPRING_DATASOURCE_USERNAME` 和 `SPRING_DATASOURCE_PASSWORD`，然后执行 `node scripts/dev.mjs --external-db --mock-ai`。此模式跳过容器管理，默认从数据库领取任务，并在本机处理资料导入。配额协调 Redis 是必需依赖，地址使用 `REDIS_RATE_HOST` / `REDIS_RATE_PORT`，兼容 `REDIS_HOST` / `REDIS_PORT`。题目缓存与 RocketMQ 按显式启用的配置连接。

直接运行后端时，在 `backend/` 中执行 `mvn package -DskipTests` 生成 JAR，再从项目根目录执行 `java -jar backend/target/zhizhida-backend-0.1.0-SNAPSHOT.jar`；也可在 `backend/` 中执行 `mvn spring-boot:run`。两种工作目录都能读取项目根目录的 `.env`。当前目录和父目录都存在 `.env` 时，当前目录中的同名配置优先，终端环境变量可覆盖文件配置。直接启动后端时，依赖服务由操作者管理，缓存和队列按应用配置启用。

IDE 或服务管理器使用其他工作目录时，设置 `SPRING_CONFIG_IMPORT` 为配置文件的绝对 URI，例如 `file:///D:/apps/zhizhida/.env[.properties]`（Windows）或 `file:/opt/zhizhida/.env[.properties]`（Linux）；也可向 JAR 传入 `--spring.config.import=file:/opt/zhizhida/.env[.properties]`。路径包含空格时给整个参数加引号；保留 `[.properties]` 扩展提示，使 Spring 按 properties 格式读取 `.env`。显式配置替换默认相对导入路径；未加 `optional:` 时，配置文件必须存在。

## 混合检索

标准 `docker compose --profile app up -d --build` 自动启动 BGE 与 pgvector，API 和 Worker 使用相同的 512 维模型与索引。首次构建需要下载模型依赖；向量数据保存在 `.runtime/compose-vectors/`，应用账号只有表读写权限。部署前可设置 `VECTOR_POSTGRES_PASSWORD` 与 `AGENT_VECTOR_PG_PASSWORD`，已有库应同步修改数据库内密码。旧 `.env` 若显式设置 `AGENT_VECTOR_ENABLED=false`，需移除该覆盖或改为 `true`。

源码运行使用以下命令启用 BM25 与向量混合检索。Docker 需处于运行状态，并已缓存 `pgvector/pgvector:pg17`；首次构建嵌入服务需要下载 Maven 依赖和模型。

```sh
node scripts/enable-rag.mjs
node scripts/dev.mjs start --mock-ai
```

第一个命令准备本地向量库和 CPU 嵌入服务，探活成功后更新项目 `.env` 的向量配置，保留 DeepSeek 密钥及其他配置。pgvector 监听 `127.0.0.1:15432`，数据与管理凭据存放在被 Git 忽略的 `.runtime/rag/`；应用账号拥有向量表的读写权限。`bge-small-zh-v1.5-q` 中文量化模型输出 512 维向量，HTTP 服务监听 `127.0.0.1:18092`，资料嵌入在本机完成。模型与运行缓存均保存在项目内。`--mock-ai` 使用演示生成模型；已有 DeepSeek 配置时省略该参数。

已有依赖时可执行 `node scripts/enable-rag.mjs --offline`。电脑重启后先重新执行该命令，再启动后端；现有后端需要重启才能读取新的配置。嵌入服务的健康地址是 `http://127.0.0.1:18092/health`。后端启动后会为已有资料登记索引任务，资料的索引状态达到 `READY` 后才具备对应版本的语义召回。

运行 `node scripts/verify-hybrid-live.mjs` 可在本机后端上创建一次性账号和合成笔记，对照相同问题的词项与混合结果。脚本验证索引 `READY` 状态、语义命中、文档版本和原文一致性，将结果写入 `docs/evidence/hybrid-live.json`，结束后删除测试账号与资料。该验证仅调用检索接口，生成模型调用数为零；派生向量的异步清理通过 PostgreSQL 单独检查。

源码交付包包含 [`services/embedding/`](../services/embedding/)。`AGENT_VECTOR_MIN_SCORE` 控制向量候选最低分，默认 0.55；改变阈值无需重建索引。启用向量后，服务异常会明确报错，不会静默变成词项结果。需要纯词项运行时，显式设置 `AGENT_VECTOR_ENABLED=false` 后重启后端。

## 模型、资料服务与端口

配置项见 [环境变量示例](../.env.example)。在项目根目录的 `.env` 中填写本机配置，源码启动时终端环境变量优先。MCP 服务默认监听本机 18091，可用 `MCP_PORT` 修改端口。源码启动器在 `AGENT_MCP_REFERENCE_ENABLED=true` 且未指定 `AGENT_MCP_REFERENCE_URL` 时管理内置资料服务；显式指定 URL 时由操作者管理该服务。Docker 部署通过内部服务名连接 MCP。

标准启动器默认启用题目缓存、提交频控和 RocketMQ 派发。使用该组合时，配置为 `QUESTION_CACHE_ENABLED=true`、`REDIS_RATE_LIMIT_ENABLED=true`、`RUN_DISPATCH_MODE=rocketmq` 和 `KNOWLEDGE_DISPATCH_MODE=rocketmq`。访问 [API 就绪检查](http://127.0.0.1:8080/api/health/ready)，确认 `data.middleware` 中的 `cache`、`submissions` 和 `dispatch` 均为 `up`；在「消息重复消费与业务落库」的解析里打开延伸阅读，可验证 MCP 查询。

直接运行后端且没有配置覆盖时，缓存和提交频控默认关闭，任务使用数据库派发，资料导入使用本地执行，向量检索默认关闭；配额协调 Redis 仍是必需依赖。标准 Docker 默认启用向量，本机启动器需先用 `enable-rag.mjs` 配置。

| 用途 | 设置 |
| --- | --- |
| 调用 DeepSeek | 设置 `AI_PROVIDER=deepseek`、`DEEPSEEK_API_KEY` 和账号可用的 `DEEPSEEK_MODEL`，重启时省略 `--mock-ai`。容器部署重新执行启动命令即可应用配置。 |
| 修改网页端口 | Docker 使用 `FRONTEND_PORT`，默认 80。本机启动器使用 `DEV_FRONTEND_PORT`，默认 5173。 |
| 修改数据库或 API 端口 | `MYSQL_PORT` 默认 3307，`BACKEND_PORT` 默认 8080。 |
| 设置数据库凭据 | 首次启动 MySQL 容器前设置 `MYSQL_PASSWORD` 和 `MYSQL_ROOT_PASSWORD`。已有数据卷使用库内保存的账号密码。 |

## 可选部署

标准 Compose 部署包含题目缓存、配额协调、消息队列和 MCP 资料服务。`docker-compose.middleware.yml` 是显式启用缓存、提交频控和队列的覆盖配置，可与标准 Compose 文件组合使用。

OTLP 导出默认关闭，`trace_id` 关联和应用指标独立启用。对接外部追踪存储时，在 `.env` 设置 `AGENT_TRACE_EXPORT_ENABLED=true` 和 `AGENT_TRACE_OTLP_ENDPOINT`，默认采样率为 10%。容器部署使用容器可达的 HTTP traces 地址。监控接口使用独立的 `METRICS_TOKEN` Bearer 凭据，留空时拒绝访问 `/actuator/**`。

拆分部署使用 `TOOL` 路由、`A1` 循环策略与 `phased-v2` 决策协议。API 与 Worker 的模型、策略和检索配置须一致。[模型输出契约](architecture.md#模型输出契约)

`LEARNING_PRACTICE_TOOLS_ENABLED` 默认 `true`，用户的历史个性化偏好默认关闭。用户允许后，新命令从 MySQL 持久观察中按能力、维度与场次召回近 180 天内最多 20 条；纠正、删除与来源撤销会使相关引用失效。`INTERVIEW_ADAPTIVE_ROUTING_ENABLED` 默认 `false`，仅控制新建普通练习的自适应路由，与记忆工具分开。

后台任务与 API 分进程运行时，叠加分进程配置。默认启动一个 API 和一个 Worker，全部副本共享 `AI_MAX_CONCURRENT_CALLS=4` 个模型调用名额和熔断状态。二者通过宿主机的 `.runtime/knowledge-shared/` 交接导入文件。所有副本连接同一个配额协调 Redis，使用相同的 `REDIS_NAMESPACE`、AI 和 SSE 限额；增加副本后，共享限额保持不变。跨主机部署需为导入目录挂载同一持久共享文件系统。

```sh
docker compose -f docker-compose.yml -f docker-compose.split.yml --profile app up -d --build
```

管理上述服务时沿用相同的 `-f` 和 `--profile` 参数，将 `up -d --build` 替换为 `config --quiet`、`ps`、`logs` 或 `stop`。分进程启动后，`ps` 应显示 `backend` 和 `worker` 都已通过健康检查。API 的就绪响应中，`data.middleware.workerEnabled` 和 `recoveryEnabled` 均为 `false`，`publisherEnabled` 为 `true`。Worker 通过容器内的健康检查报告状态。

### 共享配额与恢复机制

AI 准入与熔断通过 Lua 原子执行，冷却后全体副本仅放行一个探测请求；许可按实际模型请求超时加 30 秒余量到期，实例崩溃后自动回收。过期或旧代次的调用不能改变新熔断状态。SSE 全局默认 64 个连接、每用户 3 个，连接最多两分钟，Redis 许可 130 秒到期；连接释放只删除自己的随机令牌。清理任务用 Redis 租约与共享游标协调，丢失租约后停止推进游标，数据库事务保留幂等校验。

协调 Redis 使用 `noeviction`，与采用淘汰策略的题库缓存分实例部署。Redis 不可用时，AI / SSE 新准入返回 503。应用通过 Redis 租约协调并发，供应商网关负责供应商侧硬配额；协调数据丢失或进程暂停超过租约时，调用可能短暂重叠。更改 namespace、重建协调 Redis 或切换不兼容版本前，先排空在途调用和 SSE。

数据库派发模式每 2 秒扫描；MQ 模式通过消息唤醒任务，每 5 秒执行恢复扫描。运行扫描、SSE 轮询和 Outbox 发布使用独立调度器，Outbox 默认每 500ms 执行有界发布。任务心跳使用虚拟线程，模型并发名额由 Redis 统一分配。

面试任务在 Worker 满载、退避或执行异常时，发送两秒后可处理的延迟消息，收到发送回执再确认原通知。发送失败时，原通知在不可见期限结束后可重投。数据库扫描负责租约到期和崩溃恢复。

知识导入和索引遇到临时故障时记为 `deferred` 并 ACK，由数据库重新通知。关闭该恢复路径时，原通知到期重投。格式非法的消息发送到 `<前缀>-dispatch-invalid` 并在收到回执后 ACK。消费重试耗尽的消息进入 `%DLQ%<完整消费组名>`。

如果 Worker 一直有空槽，但有积压的 Topic 频繁出现 gRPC `DEADLINE_EXCEEDED`，可在 Broker 容器的 `/home/rocketmq/logs/rocketmqlogs/broker.log` 搜索 `Pop message error` 和 `OutOfDirectMemoryError`。Broker 写入 POP 检查点时会为线程保留编码缓冲区。内置单节点配置将发送、拉取、确认线程数设为 4、8、4，直接内存上限为 512 MiB。调整并发或消息大小后，可用下表的积压恢复用例复测。

在项目根目录运行脚本；Maven 命令在 `backend/` 执行。各项报告范围与复核结论见[运行验收记录](evidence/runtime-acceptance.md)。

明确执行真实模型验收时运行 `node scripts/verify-provider-lifecycle.mjs --real --stage=acceptance --max-requests=8 --max-output-tokens=16000`。脚本只发送合成场景，最多 8 次请求且不自动付费重跑，报告写入 `backend/target/provider-simplified/acceptance/`；再次验收使用新的阶段名。检查最终会话与逐次响应，分别记录结构校验、引用是否支持观察和持久化结果。

真实 BGE 到回答器的无答案验收使用 `KnowledgeAnswerAcceptanceTest`：启动本机 BGE，在终端设置 `RUN_KNOWLEDGE_ANSWER_ACCEPTANCE=true`、`AI_API_KEY`、`ACCEPTANCE_BASE_URL` 和 `ACCEPTANCE_MODEL`，执行 `mvn test "-Dtest=KnowledgeAnswerAcceptanceTest" "-Dknowledge.eval.embeddingPort=18092"`。测试不读取 `.env`，最多 10 次生成、每次输出上限 1500 token；报告为 `backend/target/knowledge-answer-acceptance.json`。检查无答案时 `sufficient=false` 且 `claims=[]`，正例结论有对应引文，不能以候选召回非空判定错误作答。

## 排查启动问题

### 简历导入失败

导入会保留通过校验的字段，清除不可信字段或条目，并在编辑页列出待核对项。点击提示可定位对应区域；警告随未保存草稿保留，确认保存后清除。姓名和目标岗位缺失时需手动补填。本地规则模式会明确标注。

`POST /api/resumes/import/parse` 的结果为 `draft`、`warnings`、`recognitionMode`，前后端需同步更新；创建和更新简历仍提交原保存请求。

在导入弹窗复制请求编号，用 `rg -F "请求编号" .runtime/<本次启动目录>/backend.log` 查找对应日志；Docker 部署在 `docker compose --profile app logs backend` 输出中查找。

`Resume import` 日志的 `stage` 分为 `extract`（提取正文）、`model`（模型调用）和 `validate`（字段校验）。部分成功记为 `outcome=partial`，附警告总数及各项 `field`、`reason`，例如 `field=ownerName reason=SEMANTIC_MISMATCH`；日志不包含简历正文或字段值。

错误码 `AI_TIMEOUT`、`AI_NETWORK_ERROR` 表示超时或连接失败；`AI_AUTH_FAILED`、`AI_CONFIGURATION_ERROR` 需要检查模型凭据和配置；`AI_RATE_LIMITED`、`AI_CIRCUIT_OPEN` 表示请求受限或熔断冷却。`AI_INVALID_RESPONSE` 的具体原因见同一请求的 `AI request failed` 日志；`RESUME_IMPORT_VALIDATION_FAILED` 表示返回结构无效或校验后没有可用内容。

### 启动与连接

- **本机环境检查失败**　运行 `node scripts/dev.mjs check --mock-ai` 检查工具、前后端端口和 Docker 引擎。外部数据库模式加上 `--external-db`，此时检查的是 MySQL 的 TCP 连接，账号与授权在后端启动时验证。
- **本机启动器拉取 MySQL 镜像失败**　可用 `MYSQL_IMAGE` 指定本机已有的 MySQL 8.4 镜像。有前端依赖、Maven 依赖和镜像缓存时，可使用 `node scripts/dev.mjs --offline --mock-ai` 离线启动。
- **后端启动失败**　Docker 部署查看 `docker compose --profile app logs backend mysql`。本机启动查看控制台列出的日志目录，编译错误在 `build.log`，数据库连接和迁移错误在 `backend.log`。
- **页面能打开，但请求失败**　先打开[后端就绪检查](http://127.0.0.1:8080/api/health/ready)。HTTP 503 时查看 `data.database` 和 `data.middleware.submissions`，分别对应数据库和必需的配额协调 Redis（即使关闭提交频控也会检查）。若后端就绪，再通过网页所在端口访问同一路径（默认 [Docker 代理](http://localhost/api/health/ready) 或 [Vite 代理](http://127.0.0.1:5173/api/health/ready)）。两处结果可用于区分后端依赖故障与前端代理问题。端口改动后使用实际地址。
- **代理就绪，但某个业务请求仍失败**　在[接口页面](http://127.0.0.1:8080/doc.html)复现该请求，并对照[接口定义](../contracts/openapi.json)核对认证方式与请求字段。
- **健康检查返回 200，但状态为 `degraded`**　若 `data.middleware.cache` 为 `fallback`，题库查询会回源数据库，检查 `redis-cache`。若 `dispatch` 为 `buffering`，待投递消息由数据库保存，检查 RocketMQ 和发布器日志。要验证整个练习流程，还需在网页上完成一次开场和作答。
