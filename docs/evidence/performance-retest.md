# Redis、RAG、RabbitMQ 与 MCP 性能复测

在当前工作区重新执行。缓存和消息批处理的收益得到复现；当前混合 RAG 在既有章节标注下的整体召回分数低于词项检索，延迟也更高。

环境：Windows 11、i7-14650HX、24 个逻辑处理器、31.7 GiB 内存，JDK 21、Node 24.18.1。中间件使用独占 MySQL 8.0.46、Redis 7.4.2、RabbitMQ 4.1.0；各组件计时依次执行。队列业务使用 Mock 模型，RAG 使用真实本地 BGE，无外部模型调用。

## Redis 与应用缓存

题目 `qb-java-001` 预热 10 次后，串行测量冷、热缓存各 50 次。冷组删除缓存键的时间不计入 Catalog 调用耗时。

| 指标 | 冷缓存 | 热缓存 |
| --- | ---: | ---: |
| Catalog P50 | 3.91 ms | 1.60 ms |
| Catalog P95 | 7.21 ms | 3.29 ms |
| 缓存命中 | 0/50 | 50/50 |
| 正文加载次数 | 50 | 0 |

热缓存 Catalog P95 降低 54.44%。每次调用仍检查 MySQL 中的发布状态和版本，正文加载为零不等于 SQL 查询为零。另测 20 次热缓存创建训练来源 HTTP 请求，P95 为 **14.09 ms**。

Redis 命令基准在独立容器内通过回环 TCP 执行，单个热键、256 字节值、pipeline=1、关闭 RDB/AOF；每个操作、每种并发测 10 万次，重复三轮。

| 客户端并发 | SET 吞吐 | GET 吞吐 |
| --- | ---: | ---: |
| 1 | 23,472 次/秒 | 23,594 次/秒 |
| 32 | 178,784 次/秒 | 185,529 次/秒 |

120 万次计时命令无错误，60 万次 GET 全部命中。这组容器内命令吞吐与上述经过宿主机网络、Java、MySQL 的 Catalog 延迟分别统计。

原始记录：[当前配置缓存与队列](middleware-benchmark-redis-mq-batch8.json)、[Redis 命令基准](redis-throughput.json)、[环境、命令及指纹汇总](cache-mq-performance.json)。

## RabbitMQ 任务派发

两组均为单应用进程、2 个消费者、prefetch=1、发布间隔 500 ms、批次时间预算 100 ms；分别执行三轮、每轮 12 个任务。吞吐为总计 36 个任务除以三轮总时间，P95 从合并后的 36 个样本计算。

| 配置 | 吞吐 | 排队 P95 | 端到端 P95 |
| --- | ---: | ---: | ---: |
| 旧基准：每批 1 条 | 1.94 任务/秒 | 6,002.90 ms | 6,045.69 ms |
| 当前默认：每批 8 条 | 11.16 任务/秒 | 936.98 ms | 968.71 ms |

批处理组吞吐为单条组的 **5.74 倍**。当前默认组停止消费者后积压 6 个任务，恢复消费者至全部完成耗时 **129.13 ms**；该过程保持 Broker 和 JVM 运行。

原始对照：[每批 1 条](middleware-benchmark-redis-mq-batch1.json)、[每批 8 条](middleware-benchmark-redis-mq-batch8.json)。

## RAG 检索

使用 27 份真实原文、2,398 个生产分块，其中 2,019 个可作为证据。103 道独立题包含 90 道正例、13 道资料不足题；重复三轮，每种模式保留 309 个延迟样本，三轮排名一致。质量分数以 90 道正例计算，不把重复执行当成新增题目。

本地 `bge-small-zh-v1.5-q` 为 512 维；内存向量索引，阈值 0.55，RRF K=60，两路候选各 30，章节首轮配额 2，最终返回 6。嵌入和测试 JVM 的可见 CPU 数均设为 2。

| 模式 | 标注章节 Recall@6 | MRR@6 | nDCG@6 | P50 | P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 词项 | 93.33% | 0.8202 | 0.8285 | 7.06 ms | 20.42 ms |
| 词项 + BGE 混合 | 89.44% | 0.7924 | 0.7993 | 19.20 ms | 39.69 ms |

| 分区 | 词项 / 混合 Recall@6 | 词项 / 混合 MRR@6 |
| --- | ---: | ---: |
| 开发：46 道正例 | 90.22% / 86.96% | 0.8297 / 0.7333 |
| 验证：44 道正例 | 96.59% / 92.05% | 0.8102 / 0.8542 |

整体标注召回下降 **3.89 个百分点**，混合检索 P95 为词项的 **1.94 倍**；验证分区的 MRR 则有所提高。计时从资料范围筛选后开始，混合包含本机嵌入 HTTP、内存向量查询和融合排序，不含索引构建、SQL/pgvector 或回答生成。

两路在 13 道资料不足题上均返回候选，空检索率为 **0/13**。本轮未测回答生成，不能把非空候选算作错误回答。

这些分数衡量预先标注的章节命中，标签未穷尽等价证据。例如 `JG-08` 的混合结果从“线程池参数分析”转向同文档的队列、任务执行章节；`JG-25` 从 `rows` 专节转向也介绍执行计划字段的章节。`xl-29` 则丢失了管道读取端的已标注页。报告保留逐题结果，未为了改善分数调整算法或标签。

首次检查发现 55 道题的范围超过产品最多 5 份资料的限制，现保留全部证据来源并补入同主题干扰资料，限制到 5 份；问题、答案、证据和原文不变。[范围调整记录](../../backend/src/test/resources/rag-corpus/scope-adjustments.json)保留前后范围。两种检索在修正后的同一范围重新测量，旧范围分数不参与本次比较。

原始记录：[三轮样本、分区指标、语料与模型指纹](reference-retrieval-bge.json)。

## MCP HTTP

独立 Node 服务、随机回环端口，真实 JSON-RPC HTTP 请求。31 条定向查询覆盖全部目录，topK=3；并发 1、8 交错各运行三轮，每轮 3,100 个请求，另做预热。

| 并发 | 计时请求 | 吞吐 | P50 | P95 | P99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 9,300 | 96.22 次/秒 | 11.00 ms | 16.45 ms | 20.62 ms |
| 8 | 9,300 | 1,383.20 次/秒 | 2.68 ms | 15.83 ms | 18.66 ms |

18,600 个计时请求无协议错误；31/31 条定向查询 Top1 命中，3/3 条无关查询返回空。耗时包含客户端序列化、网络往返及 JSON 解析；这是 31 条关键词目录的本机测试。

原始记录：[HTTP 样本与查询集](mcp-http.json)。

## 复跑与本次修改

在项目根目录用 PowerShell 执行；Redis/MQ 需现有 Docker 镜像，RAG 需项目内 Maven 和模型缓存。计时任务依次运行。

```powershell
$env:BENCHMARK_PUBLISHER_BATCH_SIZE = '8'
node scripts/verify-middleware-live.mjs --offline --benchmark
node scripts/evaluate-reference-retrieval.mjs
node scripts/benchmark-mcp-reference.mjs
```

将批大小改为 `1` 可复跑旧配置对照。Redis 命令基准的完整容器配置与命令保存在汇总 JSON。

中间件首次有 3 项失败，根因为测试第二个 API 实例的 Redis 命名空间被低优先级配置覆盖；已修正测试启动参数优先级。复跑 74 项单测通过，集成报告 18 项、0 失败，其中 3 项额外故障注入用例因未启用而跳过；批大小 1 的独立基准也通过。RAG 三轮各 4 项测试及 7 项资料脚本测试通过，MCP 原有 2 项测试通过。

本次未修改生产检索和中间件实现。历史证据保留，独占容器、数据库、嵌入服务及临时文件已清理。
