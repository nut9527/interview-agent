# 面试 Agent：计划、难度、动态追问与复盘

更新：2026-10-28。首页与登录后默认进入 `/interview`。导航仅保留面试训练室、简历管理、目标岗位、账号设置。

## 使用与材料

选择已保存目标岗位，或直接填写本场自定义岗位名称和 JD（最多 20,000 字）。两种来源互斥；自定义 JD 不创建目标岗位，但完整原文固定在本场记录。已保存岗位按本人归属与 revision 校验，之后修改/删除源岗位不会影响本场快照。

简历可从列表选择、从 PDF/DOC/DOCX 导入并核对保存，或新建填写。简历管理拆为 `/resumes` 列表与 `/resumes/edit` 编辑页，保留预览、版本历史和 AI 优化。目标岗位仍支持 CRUD、JD 导入、要求拆分与简历原文对照；从岗位带材料进入训练室会打开新场准备。

## 难度与配置

| 值 | 界面 | 提问侧重 |
| --- | --- | --- |
| `BEGINNER` | 入门 | 基础概念、个人职责、清晰引导 |
| `STANDARD` | 标准（默认） | 真实岗位实践、方案选择、验证依据 |
| `ADVANCED` | 挑战 | 复杂约束、技术原理、备选方案、故障边界与迁移 |

难度不改变总轮次或允许动作。V23 保存 `difficulty`，旧面试默认标准难度。首问、后续评审、修正调用都从本场原值构建服务端难度策略；JD 和回答中的指令不能覆盖策略。Mock 也显示对应问题深度，完整能力判断仍需真实模型验证。

界面默认综合能力、6 轮，可选 3/6/9/12 轮；后端支持 1–12 轮，并保留旧请求缺省轮数行为。方向支持综合能力、后端基础、项目深挖。原诊断关联项目练习入口与接口已删除。

## 专项训练与薄弱点复练

准备页切换“专项训练”，选择数据库、并发、性能或项目深挖，设置三档难度及 3/4/5/6 轮。简历与岗位为可选材料，缺少材料时使用情境题。启动请求增加可选 `trainingTopic`（`DATABASE/CONCURRENCY/PERFORMANCE/PROJECT`）；服务端固定数据库、并发、性能对应的单一能力，项目主题考察职责与方案取舍。仍按实际回答选择追问策略，所有轮次围绕所选主题。

复盘卡片的“复练此能力 · 3 轮”直接发起新场，请求只携带 `retrySessionId/retryRound` 和轮数等基础字段。服务端校验本人已完成的原会话和真实评估轮次，从原记录读取能力、问题、完整回答、证据与缺口，沿用原场岗位、简历快照及难度，不接受客户端伪造缺口或混入新材料。复练接口也支持 3～6 轮，界面一键入口固定 3 轮。

训练信息保存在 `agent_json.training`，与逐轮评估一同提交，不增加数据库迁移。`interview-training-v1` 中单能力最多追问 5 次，项目双能力每点最多追问 2 次，保证最多 6 轮仍可走完计划。旧综合面试预算保持原规则。原回答仅放入模型的 `untrustedEvidence.retry`，不能作为本场新证据；输入压缩只影响模型上下文，不截断数据库中的原回答快照。

复练页提供“前后对照”，展示原问题、回答全文、证据、缺口及本次逐轮回答、证据和仍待补充项，可打开原会话；原会话通过 `GET /api/interviews/sessions/{id}/retries?page=1&size=20` 分页查看关联复练。两个方向都按当前账号归属校验。删除原会话后，已创建复练仍保留发起时快照；原会话链接会返回不存在。账号注销和演示数据回收随整个会话清理快照。

Mock 只演示追问与对照流程，不能判断旧缺口是否在语义上已补齐；真实模型的缺口核对质量仍需单独验收。浏览器验收入口：`node frontend/scripts/verify-training-browser.mjs`（先构建前端，可用 `PLAYWRIGHT_MODULE` 指向已有安装），记录见 [专项训练浏览器验收](evidence/2026-10-28-training-browser.json)。

本次后端单元/Web、隔离 MySQL、覆盖率与前端验证范围见 [2026-10-28 专项训练验证](evidence/2026-10-28-training.json)。

`AI_PROVIDER=mock` 可以无密钥体验完整后端 Agent 流程；`deepseek` 使用真实模型。独立求职准备 Agent 已删除，面试无需它的开关或 SDK。

## 决策循环与约束

1. `InterviewAgentPolicy.plan` 根据模式、轮数、JD、简历事实和近期练习计数生成 `interview-agent-v3` 计划，长度为 `min(rounds, 8, ceil(2*rounds/3)+1)`。
2. 服务端计算当前能力、下一能力及允许动作，模型读取固定材料、精简记忆和回答记录。
3. 模型返回反馈、下一问题或总结，以及 `agentDecision`：能力证据等级、当前回答原文、缺口、动作、下一能力 ID、依据、训练任务、`probe` 策略和最多 200 字的 `intent`。它们描述下一问；评估另存由服务端从上一条决策导出的 `answeredProbe/answeredIntent`，以免把下一问策略误记为当前回答的策略。
4. 服务端校验枚举、长度、引用、目标、预算、策略去重及历史问题文本重复。模型还需声明 `questionCompetencyId`：非结束时与下一目标 ID 一致，结束时为空字符串。存储、并发、性能三类问题增加技术主题弱校验，拦截声明存储却只问线程安全等明显错位。校验失败带原因修正一次；通过后才用原租约 CAS 同次提交。
5. 结束后前端从已保存评估生成能力覆盖和训练清单，不额外调用模型。

`FOLLOW_UP` 只追问当前能力；`ADVANCE` 只进入计划中的下一能力；`FINISH` 仅最后一轮允许。`followUpBudget = 剩余轮数 - 尚未考察能力数`，新计划每点最多追问两次。允许推进前还要检查后续能力的轮次容量：`剩余轮数 <= 后续能力数 * 3`。模型不能一路推进后把五轮留给最后一点；12 轮仍为 8 点加 4 次追问，每点最多三次回答，且全部能力均能覆盖。旧计划保留原有容量，不对已进行的会话强加新上限。

追问策略有 `EVIDENCE`（证据）、`QUANTIFY`（量化）、`COUNTEREXAMPLE`（反例）、`TRANSFER`（迁移）、`TRADEOFF`（取舍）、`CLARIFY`（澄清）。同一能力优先使用尚未使用或使用最少的策略，并排除上一种策略；切换能力使用 `OPENING`，结束使用 `NONE`。历史问句按标点、空格和大小写归一去重；语义改写仍依赖模型遵守意图约束，规则无法保证识别所有近义问题。

`INSUFFICIENT/PARTIAL/STRONG` 分别显示“证据不足／部分体现／充分体现”。非不足等级必须引用至少四个字符；任何非空引用都必须是最新回答的连续原文。候选人自述不等于独立验证，引用存在也不证明模型语义判断正确。系统不产生招聘通过率或综合能力分。

开场和评审均允许一次修正：模型正文 JSON 不完整、字段结构、引用、动作、策略、问题目标等失败时，携带 `validationFailure` 要求重出完整 JSON。开场还必须返回与首项能力一致的 `questionCompetencyId`，两次失败不创建半成品会话。上下文解码、输入预算、网络、鉴权、准入和迟到提交失败不属于可修正输出，不重复调用模型。

一次修正不重复扣用户分钟或每日额度，由原请求覆盖；仍消耗全局每日资源预算两单位，保留模型令牌计量、并发和超时限制。初次调用的准入消耗沿用既有规则，最终失败也不退款。Agent 回答租约覆盖两次超时加 15 秒，前端回答等待 90 秒。两次失败释放租约，不保存半轮结果；浏览器按用户、会话、1–12 轮保留原回答及请求编号 10 分钟。已提交请求回放不再调用模型或扣额。

正常调用沿用 `INTERVIEW_OPENING/INTERVIEW_REVIEW`，修正独立记录 `INTERVIEW_OPENING_REPAIR/INTERVIEW_REPAIR` 的成功、失败和耗时，评审修正不再重复记为正常评审。可用 `zhizhida_business_seconds_count{operation="interview_repair"}` 与 `operation="interview_review"` 的增量之比观察全量评审的修正尝试比例，再按 `outcome` 查看成功率。指标仅含有限操作和结果标签，不带用户 ID、材料、问题或拒绝原因原文。

## 持久化、上下文与兼容

Flyway V22 的可空 `interview_sessions.agent_json` 继续保存全部 Agent 状态，V23 另为本场难度增加持久化字段。计划、执行模式、当前能力和逐轮评估与对话同属一行，同次租约条件更新。无 Agent 的旧会话继续原流程；v1 计划仍可继续，旧决策缺失的策略元数据保持未知，不倒填历史。旧项目准备快照保留读取兼容，独立项目复盘接口和诊断入口已退役。

模型输入中的 `agentCheckpoint` 和 `agentRouting` 只使用从固定能力库重建的定义、ID、枚举和预算，即使读取含用户原文的 v1/v2 目标也不直接信任。材料锚点、旧目标原文、历史证据摘要和历史模型文字均放入 `untrustedEvidence`；提示词明确这些文本中的指令不得执行。`targetRole/resumeSnapshot/transcript` 同样是不可信素材。这是数据与控制边界隔离，不能保证真实模型永不受提示注入影响。

每轮提交时从已验证的引用构建 `digest`：轮次、能力 ID、等级、最多 120 字证据、100 字缺口及实际接受的策略，与对话同次保存、同次回放截断。模型压缩旧 transcript 后仍读取每轮摘要。该摘要是证据摘录，不是额外模型生成的完整事实总结，无法替代原文；数据库完整问答一直保留。

输入只提供当前、下一能力的材料引用与最多两项相关历史计数；输出预算 2000 token，输入上限 30000 字符。最新回答保留全文，旧全文按预算缩短；极端转义压力下会缩短摘要和引用片段，同时保留每轮摘要条目，并标记 `contextTruncated/digestCondensed`。确定性的预算错误原样返回，不进入修正路径。

开始时按本人、同模式、已结束状态读取最近八份 Agent 检查点，仅查询 `agent_json`，不加载旧简历或对话。按能力与 `answeredProbe` 聚合回答次数、证据不足和部分体现次数，并过滤不同执行模式，避免 Mock 评估影响真实模型计划。计数以最多三分的有限权重参与计划排序；模型只见当前相关计数。缺失策略的旧历史保持未知。删除历史后不会参与将来的新计划；已开始会话的计划与计数快照保持固定。

这是面试专用的受约束 Agent 循环：规则生成计划，模型在允许动作内决策，跨会话只使用有限的本人练习计数。没有开放工具执行、浏览器检索或独立长期记忆库。问题目标 ID 和技术关键词只提供弱语义约束，无法保证完整语义一致性或识别所有近义改写。真实模型端到端与旧业务库升级演练未在本次回归中执行。
