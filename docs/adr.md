## ADR-003：使用可撤销 Bearer Token，并严格隔离用户私有数据

- 状态：`已采纳`
- 首次落地：2026-07-10，账号持久化提交 `766de12`；2026-07-14 完成安全加固 `d436a35`

背景：项目没有复杂角色体系，但需要保护个人资料、简历、私有目标岗位和面试记录，并支持退出、修改密码后使旧会话失效。

决定：密码使用 BCrypt 哈希，登录成功后生成高熵随机 Bearer Token，客户端保存原 Token，服务端只保存 Token 的 SHA-256 哈希和过期时间。标准会话默认有效 24 小时，退出可撤销当前会话，修改密码会撤销该用户全部会话。所有用户私有资源的查询、修改和删除必须同时包含当前用户 ID 条件；访问他人资源按不存在处理。

影响：每个受保护请求需要查询会话状态；后端服务和 Repository 方法必须持续传递用户 ID。任何绕过 `CurrentUserProvider` 或只按资源 ID 操作的数据访问都应视为安全缺陷。

## ADR-011：使用分层自动化测试与覆盖率质量门禁

- 状态：`已采纳`
- 首次落地：2026-07-14，测试强化提交 `69c3af1`、`7eed456`

背景：项目代码繁杂，仅依赖人工演示无法提供足够快的回归反馈。

决定：后端使用 JUnit 5、Mockito 和 MockMvc 编写单元测试，使用独立 `*IntegrationIT` 测试验证数据库、鉴权和完整业务闭环；Maven Surefire 与 Failsafe 分工执行，JaCoCo 在 `verify` 阶段检查行覆盖率和分支覆盖率，当前门槛均为 80%。

影响：数据库集成测试需要可用的测试环境，执行时间长于单元测试。每次修改应先运行相关测试，再按风险运行完整验证；任何因环境原因跳过的测试必须明确记录，不能写成通过。

## ADR-013：使用 ArchUnit 执行模块与分层约束

- 状态／日期：`已采纳`，2026-10-01。
- 问题：已有 `jdeps` 测试需手动解析输出、遍历依赖环，缺少覆盖所有 Controller 的持久层检查；文档和实际规则易脱节。
- 方案：引入仅测试范围的 ArchUnit 1.5.1，生产字节码排除测试类；用 API 包约束模块访问、slices 验证依赖环，增加核心规则基础设施禁令与 Controller 分层约束，保留原管理 API、模型适配器与面试严格白名单。健康探针数据库访问移到 `ReadinessService`。
- 放弃的方案：继续扩充 `jdeps` 自定义解析；立即拆 Maven 多模块；立即引入 Spring Modulith。当前需要的是可执行约束，后两项增加配置与迁移范围。
- 代价：增加测试依赖与字节码扫描耗时；新模块／旧包核心类需同步登记；静态依赖检查不覆盖反射和运行时 SQL 行为。反例由 JDK 编译后检查并自动清理。
- 验证证据：[ModuleBoundaryTest](../backend/src/test/java/cn/edu/whu/zhizhida/architecture/ModuleBoundaryTest.java)、[规则反例](../backend/src/test/java/cn/edu/whu/zhizhida/architecture/ArchitectureRulesTest.java)、[健康接口测试](../backend/src/test/java/cn/edu/whu/zhizhida/health/HealthControllerTest.java)；后续完整回归见 [2026-10-04 记录](evidence/2026-10-04-core-rules-contracts.json)。
- 复审条件：确需模块级集成测试或自动模块文档时再评估 Modulith。[官方验证](https://docs.spring.io/spring-modulith/reference/verification.html)覆盖公开接口与模块依赖；[1.2 兼容表](https://docs.spring.io/spring-modulith/reference/1.2/appendix.html#appendix.spring-boot-compatibility)的编译基线为 Boot 3.3，示例包含 3.3，与该决策时的 Boot 3.3.5 同系列。本次仅查表，尚未在项目试装；当前已[升级 Boot 4.1.2](Java21与SpringBoot41迁移.md)，引入时须重新核对目标版本、维护状态和传递依赖。ArchUnit 依据：[官方示例](https://www.archunit.org/use-cases)。

## ADR-015：面试采用可配置轮数、纯规则与租约应用编排

- 状态／日期：`已采纳`，纯规则提取于 2026-09-30，2026-10-01 补记；替代原面试决策。
- 问题：固定三轮和混合身份、模型、存储的状态机不易单独验证；超时重试与迟到响应可能重复提交或扣额。
- 方案：支持 1–12 轮，界面默认 6 轮，兼容旧请求缺省 3 轮；保存岗位/JD、简历修订快照及面试难度。`InterviewTransitions` 决定题号、回放和结束；`InterviewStateMachine` 负责身份、额度、模型、租约和提交，模型在服务端允许动作内选择追问或推进，并生成问题、反馈与结构化证据；状态、预算和原文引用仍由服务端校验。先判断回放与规则，再领租约和扣额，事务外调用模型后条件提交。
- 放弃的方案：让 AI 决定状态；在数据库长事务内调用模型；仅用 JVM 锁阻止重复回答。
- 代价：租约有效期和重试编号要贯穿接口与前端；模型完成后进程崩溃仍可能导致重试再次调用，数据库幂等不保证供应商恰好一次计费。
- 验证证据：[纯规则与边界](evidence/2026-09-30-interview-rules.json)、[实库租约测试](../backend/src/test/java/cn/edu/whu/zhizhida/interview/InterviewAnswerIntegrationIT.java)、[回放额度测试](../backend/src/test/java/cn/edu/whu/zhizhida/interview/InterviewAnswerReliabilityTest.java)。

## ADR-017：AI 优化建议与表单草稿分离

- 状态／日期：`已采纳`，2026-10-02。
- 问题：个人简介在模型回包时直接覆盖表单，缺少差异审阅、部分采用、拒绝和撤销；等待模型／保存时继续输入可能丢失文字。
- 方案：每个字段独立控制器，生成捕获文本与岗位，只展示有界文本差异；采用前重新核对当前值。按批次保存逆向撤销信息，保留不重叠的手工编辑；项目使用稳定表单 key，卸载／账号切换中止并隔离旧请求。保存只更新 revision，首次创建延续编辑实例。
- 放弃的方案：整段回填再让用户自行恢复；让模型输出可信偏移；全表单禁用直到模型返回；持久化服务器端建议工作流。当前范围用已有 rawText 接口和本地文本比较即可完成交互闭环。
- 代价：建议／撤销栈只在当前编辑页保留；采用前字段变化需重新生成，重叠手改保守拒绝自动撤销；超过 200 个分段时合并差异。取消客户端等待不保证模型调用取消或退款。
- 验证证据：[设计与边界](AI优化比较与撤销.md)、[15 项专项／60 项前端回归及 11 个浏览器场景](evidence/2026-10-02-ai-review.json)。无后端／数据库修改，真实模型效果与直连后端浏览器联调未验证。

## ADR-018：导入先审阅，编辑以基线、草稿和修订号管理

- 状态／日期：`已采纳`，2026-10-03。
- 问题：导入直接创建错误数据，刷新丢失编辑；409 只提示错误，保存与切换账号的迟到响应可能破坏草稿。
- 方案：新增鉴权但不落库的 parse 接口，纠正后复用创建。控制器分开基线／当前表单，sessionStorage 按账号／简历保存 24 小时；保存只确认提交时快照，初次创建迁移键。409 读取最新版，比较基线与双方修改并让用户选择，继续携带 revision。同步提交锁、读取序号、AbortSignal 和账号代次隔离异步响应。
- 放弃的方案：后台定时保存到正式简历（增加历史噪声且无法区分确认）；localStorage 多标签页共享草稿（易互相覆盖且保留过久）；遇到冲突强制覆盖或按数组下标自动合并。当前范围无需新增草稿表或协作编辑协议。
- 代价：草稿只在本标签页有效，退出／换号清理；存储容量不足时仅内存保留。结构化列表整体选择，创建超时需核对列表，尚无服务端创建幂等。旧直接导入及可省略 revision 的契约仍兼容。
- 验证证据：[可靠性设计](简历编辑与导入可靠性.md)、[18 项专项／78 项前端回归、595 + 132 后端测试和 11 个受控浏览器场景](evidence/2026-10-03-resume-editor.json)。无新增依赖／迁移，未部署或执行浏览器直连后端联调。

## ADR-021：保留模块边界，以纯计算和契约基线约束演进

- 状态／日期：`已采纳`，2026-10-04。
- 问题：规则与身份、存储或模型编排混合时难以独立验证；按错误文案分支不稳定；后端 DTO 与手写前端类型可能静默漂移。
- 方案：私有岗位与面试规则保留在各自 domain，Service 负责权限、事务和调用编排，ArchUnit 限制五个业务模块的依赖方向并核验白名单类型存在。统一响应新增 ErrorCode，保留原字段和 HTTP。无数据库 Web 测试导出真实 OpenAPI 并比较快照，无依赖脚本生成 TS，编译断言核对 UI DTO；GitHub Actions 用目标分支契约识别不兼容变更，更新快照不能绕过；本次明确退役项由专门清单限制范围。
- 放弃的方案：微服务／Maven 多模块（当前只需约束依赖，部署拆分增加成本）；只验证快照文件一致（重新生成即可放过破坏）；全量替换页面模型（旧快照 optional／null 与 UI 窄类型仍需兼容）；新增通用 SDK 生成框架（当前 schema 子集可由小脚本明确支持并测试）。
- 代价：生成器需随 OpenAPI 特性扩展且未知结构直接失败；兼容检查保守，部分约束放宽也会拒绝。UI 断言允许旧 optional／null 和一般 String 的窄化，无法证明未声明业务语义。新页面 DTO 需登记断言，新增码及破坏性接口需版本迁移评审。
- 验证证据：650 项单元／Web、148 项隔离 MySQL、86 项前端、7 项契约测试和 4 项编译反例、类型／lint／构建与覆盖率双 80% 门禁通过。完整 [设计](核心规则与接口契约.md) 与 [验证记录](evidence/2026-10-04-core-rules-contracts.json)。远程 CI 未运行，无新依赖、迁移或部署。
